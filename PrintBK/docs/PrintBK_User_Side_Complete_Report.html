1. Executive Summary & Core Objectives

PrintBK is an ultra-low latency, serverless self-service printing web application tailored for high-volume campus print shops. Designed specifically for HKBK Student Point, it allows students to walk up to the counter, scan a QR code on their smartphone, select files from cloud or local storage, customize print options in real time, view accurate page counts and live previews, and submit orders with a verified 4-digit pickup code.

1.1 Project Challenges Solved

Challenge Previous Behavior Implemented Solution
Presentation Previews PPTX files showed missing or blank previews, or basic text-only summaries. Integrated @aiden0z/pptx-renderer for full vector slide-by-slide rendering (shapes, fonts, layout, backgrounds) with live slide navigation.
Slide / Page Accuracy Presentations stuck on "1 page" regardless of true slide count (e.g. 9 slides). Multi-strategy OpenXML ([Content_Types].xml, presentation.xml, normalized slide paths) and CFB OLE2 parser for exact slide detection.
Upload Transition Flashed an empty basket screen or blank view during file processing. Immediate synchronous transition in filePicker.ts to an animated "Processing your documents…" state.
File Integrity & Quality Risk of client-side canvas compression degrading student print quality. Original raw binary streams cached in memory (rawFileMap) and uploaded byte-for-byte to cloud storage without downscaling.
Price Breakdown UI Text overlapping, cramped layout, and missing mathematical calculation formulas. Overhauled BreakdownSheet.tsx with explicit formulas (₹1.50/p × 10 pages × 1 copy) and zero overlapping.
UI Button Hygiene Duplicate floating ✕ buttons and confusing close/delete actions. Suppressed top-right floating close button (noTopClose); implemented dedicated red checkout-style close button and separate trash button.
Pickup Code Tracking Pickup code was generated on the fly and unsaved on the backend. Unified 4-digit code generated during checkout, saved in Catalyst Data Store, returned via API, and matched on ticket & receipt.

2. System Architecture & End-to-End Pipeline

The system follows a distributed edge + serverless model, minimizing server costs while guaranteeing zero infrastructure maintenance for the shop owner:

1
Student Scans Counter QR Code

Loads PWA/SPA from Zoho Catalyst static hosting (https://printbk-.../app/index.html) onto the student's mobile browser.

2
File Selection & Client-Side Heavy Lifting

Native file picker accepts PDF, DOCX, PPTX, Images. The browser executes page counting (Web Worker / JSZip) and caches the raw File binary in rawFileMap.

3
Instant Live Document Preview

PDFs render via PDF.js; presentations render via PptxViewer. Switching between B&W and Colour dynamically applies CSS filters in real time.

4
Authoritative Checkout & Order Generation

Student generates a 4-digit pickup code. Client sends basket to POST /server/api/orders. The backend recalculates exact math prices to prevent frontend tamper attacks.

5
Payment & Ticket Screen

Student pays via dynamic UPI QR / Intent or reserves for Cash at Counter. Upon payment, status shifts to processing, and the student ticket shows the final pickup code.

6
Seller / Counter Desktop Agent Ingestion

Shop PC polls GET /server/api/orders, matches pickup code when student arrives, prints to system printers, and transitions status to completed.

3. User Side Feature Implementation Details

3.1 High-Fidelity PPTX Slide Renderer

To satisfy the requirement of rendering the original presentation design rather than an unformatted text extraction, PrintBK integrates @aiden0z/pptx-renderer directly into the React lifecycle:

  • Mounting Safety: The container element pptxContainerRef is explicitly set to display: block with measurable geometry prior to calling PptxViewer.open(...), eliminating zero-dimension scaling bugs.
  • Interactive Pagination: The viewer controls are synchronized with the user's slide slider. Clicking [ Next ▶ ] or [ ◀ Prev ] calls viewer.goToSlide(page - 1) while displaying Slide X of Y.
  • Live Grayscale Contrast: The CSS filter grayscale(100%) contrast(140%) brightness(102%) is applied instantly when the student selects B&W mode, allowing them to verify readability before printing.
  • Automatic Store Sync: If viewer.slideCount detects more slides than the initial fast counter, it automatically updates useBasket.getState().updateFile(file.id, { pages: count }) so the price recalculates accurately.

3.2 Multi-Strategy Slide & Page Counter

Located in student/src/lib/pdfPages.ts, the counting engine uses a cascading multi-tier strategy:

File Type Primary Inspection Strategy Fallback Strategy
.pptx [Content_Types].xml: Counts occurrences of presentationml.slide+xml. ppt/presentation.xml (<p:sldId> tags) followed by normalized regex matching ppt/slides/slide*.xml and ppt\slides\slide*.xml.
.ppt (Binary) CFB (OLE2) library: Inspects DocumentSummaryInformation stream for PIDDSI_SLIDES (0x10) record. Inspects PowerPoint Document stream for RT_SlidePersistAtom (0x03F8) and RT_Slide (0x03EE) records.
.docx docProps/app.xml: Extracts <Pages>N</Pages>. Counts paragraph clusters and manual section break markers in word/document.xml.
.pdf pdf-lib: Loads binary array buffer with ignoreEncryption: true and calls pdfDoc.getPageCount(). PDF.js fallback worker parsing.

3.3 100% Original Upload Quality Assurance

Unlike conventional web tools that re-render documents onto canvas and re-encode them as lossy JPEGs (causing fuzzy text and blurry diagrams), PrintBK implements an uncompressed memory pipeline:

Zero-Compression Guarantee:
The moment a user selects a file, the raw browser File instance is placed into rawFileMap.set(file.id, rawFile). When dispatched to the cloud via api.uploadFile(raw), the unaltered binary buffer is transmitted directly through FormData. The exact SHA-256 byte stream selected by the student is what arrives at the shop printer.

3.4 Pricing Model & Mathematical Breakdown

Exact rates enforced across both client and server:

  • Black & White (1-Sided): ₹1.50 per sheet
  • Black & White (2-Sided / Duplex): ₹0.85 per physical page
  • Colour (1-Sided & 2-Sided): ₹8.00 per physical page
  • Bulk Discount Tier: ≥100 sheets automatically discounts B&W rate to ₹0.80/page
  • Add-on Services: Spiral Binding (₹30), Hard Cover (₹150), Lamination (₹25), Scanning (₹5)

4. Backend Architecture & API Reference

The backend runs as a Zoho Catalyst Advanced I/O function in Node 18, backed by Zoho Catalyst Data Store with ZCQL queries.

4.1 Orders Database Schema (ZCQL)

Column Name Data Type Description
id VarChar (PK) UUID identifier for the order (e.g. 34c882d4-f46e-4557-...).
status VarChar State lifecycle: pending_payment, processing, printing, ready, completed.
basket LongText (JSON) Full basket payload including file options, pages, colors, services, and pickupCode.
file_names LongText (JSON) Array of original file names associated with the order.
quote_pending Boolean Flags custom services requiring counter price confirmation.
total Double Authoritative total in Indian Rupees (INR).
created_at BigInt Unix epoch timestamp of creation.
updated_at BigInt Unix epoch timestamp of latest status update.

4.2 API Endpoint Directory

POST /server/api/upload

Accepts multipart/form-data containing file. Limits to 25MB. Verifies MIME firewall against PDF, Office, and images. Streams binary to Catalyst File Store in the print_files folder and returns { cloudId, name, size }.

POST /server/api/orders

Accepts JSON payload containing { files, services, rush, pickupCode }. The backend executes strict type validation, anti-negative sheet checks, and computes the authoritative total. Inserts record into orders and returns { orderId, status, total, quotePending, pickupCode }.

GET /server/api/orders

Returns array of all active orders sorted by created_at DESC. Parses the nested basket JSON to expose pickupCode, basket, fileNames, and total for the seller dashboard.

GET /server/api/orders/:id

Retrieves specific order details, payment status, and pickup code for the student's ticket screen.

POST /server/api/orders/:id/pay

Called when student verifies UPI payment or confirms cash reservation. Updates order status to 'processing'.

POST /server/api/orders/:id/status

Used by the seller/counter dashboard to advance order progress. Accepts { status: 'printing' | 'ready' | 'completed' }.

5. Seller / Counter Side Integration Handbook

With the user/student side finalized and live, the counter/seller side connects seamlessly using the existing backend contract. Below is the operational workflow for connecting the seller interface:

5.1 Counter Order Verification & Pickup Matching

A
Student Arrives at Counter

The student displays their ticket screen featuring their 4-digit PICKUP CODE (e.g. 4821) and Order ID (e.g. #9BFF0C).

B
Seller Enters Code or Inspects Live Feed

The counter interface polls GET /server/api/orders every 4–5 seconds. The seller types 4821 into the search box or clicks the newest incoming card in the queue.

C
Spooling to Printer

The seller clicks "Print Job". The print agent downloads the original uncompressed file from Catalyst File Store and dispatches it directly to the local Windows or CUPS printer.

D
Order Status Transition

The counter interface fires POST /server/api/orders/:id/status with { status: 'ready' }. The student's phone automatically updates their progress step to Ready!.
